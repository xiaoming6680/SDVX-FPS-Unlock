# 逆向记录

分析对象：`soundvoltex.dll`，版本 `KFC:J:G:A:2026101300`（PE TimeDateStamp `0x6ac4e43b`，入口 `0x7ad8d8`）。
以下地址均为 RVA，另注明的除外。工具：Python + capstone 线性反汇编、RIP 相对引用索引。

## 现象

- 游戏 Present 用的是 `D3DPRESENT_INTERVAL_IMMEDIATE`（不开垂直同步），在 300Hz 屏幕上帧数仍精确为 120.00。
- 已有的 Game FPS Target / Note FPS Target 补丁设成 300 后帧数不变，说明另有限帧逻辑。

## 已有的两个补丁做了什么

- `GetMainDisplayRefreshRate`（`0x3e5850`）：通过 NVAPI（`NvDisplayConfig`）读主显示器刷新率，返回 double（Hz）。
  读取失败时返回 `.rdata` 里的常量 60.0（`0x9844e8`），并打印 `(DUMMY)`。
- **Game FPS Target**：改的就是这个 60.0 回退值。
- **Note FPS Target**：把 `movd xmm6, eax; cvtdq2pd; mulsd [0.001]`（毫赫兹转赫兹）替换为 `mov eax, N; cvtsi2sd xmm6, eax`，
  即无论屏幕多少 Hz，都告诉游戏刷新率是 N。音符滚动速度按这个值计算。

## 内部限帧器

一个全局对象，位于 `0x12d4780`（由函数局部 static 守卫 `0x12d4778` 初始化）：

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0 | int32 | 基础帧率，毫赫兹，初始 60000 |
| +4 | int32 | 目标帧率，毫赫兹，0 表示不限帧 |
| +8 | int64 | 下一帧截止时间，纳秒 |

相关函数：

| RVA | 作用 |
|---|---|
| `0x6119b0` | 取对象指针（17 处调用） |
| `0x6119f0` | `set(rate)`：写 +0，清 +4，重置截止时间 |
| `0x611a40` | 重置截止时间为当前时间 |
| `0x611a90` | 等待：+4 非 0 时，截止时间 += 1e12 / rate，然后 `SwitchToThread` 自旋到截止时间 |

设置点在 `0x5a1979` 附近（显示初始化流程）：

```
edi = 60000
if (check_0x1d5c90()) {             // 当前环境走这一支
    lim->set(120000)                // 0x5a1987: mov ebx, 0x1d4c0
    lim->target = has_cfg ? cfg : 120000
    lim->reset()
} else if (check_0x1268d0()) {
    lim->set(60000); lim->target = has_cfg ? cfg : 60000; ...
} else {
    lim->set(60000)
}
```

`0x5a1a20` 起的函数会把「有效帧率」（target 非 0 取 target，否则取 base）返回给游戏其他部分，所以一部分逻辑会随之缩放。

## 补丁

把 `0x5a1987` 的 `mov ebx, 120000`（`BB C0D40100`，文件偏移 `0x5a0f87`）改成 `mov ebx, N*1000`。
三项补丁需取同一个 N：限帧器决定实际帧数，Game/Note FPS Target 让游戏按同一速率计算。

安装脚本用特征码定位，不写死偏移：

```
BB C0 D4 01 00   mov ebx, 120000
8B D3            mov edx, ebx
48 8B C8         mov rcx, rax
E8               call set
```

要求在整个 dll 里**正好命中一处**。2026101300 与 2026071400 两个版本均唯一命中。

## 补丁文件

spice2x 按 `patches/KFC-<TimeDateStamp:08x>_<AddressOfEntryPoint:x>.json` 加载补丁。脚本：

1. 读 dll 的 PE 头得到文件名。
2. Game FPS Target：校验 dll 中 60.0 的 8 字节（`0000000000004E40`），改为写 double 的高 2 字节，使所有档位覆盖同一范围（原补丁只写 1 字节，180 / 185 等需要 2 字节）。
3. Note FPS Target：校验 60 档原始字节，按 120 档的指令格式生成其他档位。
4. 插入 Frame Limiter Target 联合补丁，重复运行结果相同；首次运行备份原文件。
5. 插入 Knob Fix for High FPS 开关补丁（`type: memory`，见下文「菜单旋钮」）。特征码不是正好一处时只提醒、不加这一项，其余照常安装。

档位 = 预设（60 / 120 / 144 / 165 / 180 / 185 / 240 / 300）加上玩家输入的数（60–1000）。Game FPS Target 只写 double 的第 5、6 字节，最高字节固定 `0x40`，2–8191 的整数都能精确表示。

### 安装器自动完成的设置

- **显示器**：`EnumDisplayDevices` / `EnumDisplaySettings` 列出每个显示器当前分辨率下支持的刷新率。游戏显示器取 `spicetools.xml` 里 Sound Voltex 的 `mainmonitor`，没设就取主显示器。默认目标帧数 = 游戏显示器最高刷新率。
- **竖屏判断**：这里的「竖屏」指游戏会走 1080×1920 全屏 + 垂直同步那套。游戏启动时（`0x5a0c3f` 起）用 `GetAdapterModeCount` / `EnumAdapterModes` 在模式列表里按顺序找 1080×1920@120、1080×1920@60，选中的刷新率在 UFC 下等于 120 就用 `INTERVAL_ONE`（`0x5a105d`），否则 `INTERVAL_IMMEDIATE`。1080×1920 的模式只在显示器转成竖屏时才有，而很多启动器平时让屏幕保持横屏、开游戏时才转，所以安装器优先看 `contents\log.txt` 里 spice 记下的上次启动 `fullscreen display mode for adapter 0: ... RefreshRate: N`（游戏请求的值，`-graphics-force-refresh` 改之前），N = 120 当竖屏、其它当横屏，并显示在「上次启动」一行；日志里没有这一行时才看当前桌面高是否大于宽。对照：2026101300 横屏 2560×1600 的日志是 1080×1920@60 + `Using D3DPRESENT_INTERVAL_IMMEDIATE`，issue #1 竖屏 480Hz 的日志是 1080×1920@120 + `force refresh rate: 120 => 480 Hz`。刷新率列表取显示器 1080×1920 和 1920×1080 两种模式，所以桌面是横屏时也能列出竖屏全屏可用的刷新率。
- **配置文件位置**：从 `contents\log.txt` 开头记录的上次启动参数读 `-cfgpath`（`spicetools.xml`）和 `-patchcfgpath`（补丁选择），相对路径相对 `contents`。读不到时依次找 `contents\`、`%APPDATA%\spice2x\`、`%APPDATA%\`。都没有就提示玩家在 F4 里手动选。
- **补丁选择**：spice2x 把联合补丁的选择存在 `union_patches_enabled`，键为 `sha256(补丁的 gameCode + 补丁文件名（不含 .json） + 补丁名 + description)` 的小写十六进制，值为选中的档位名。本机配置里 8 个补丁的哈希全部按这个公式复现。安装器写入三项的档位名，并把 `prop\ea3-ident.xml` 的 `model:dest:spec:rev:ext` 加进 `auto_apply`（spice 启动时按它自动套用已保存的选择）。所以 Frame Limiter 的 description 不能随便改，改了哈希就变，旧的选择会失效。开关补丁的开启状态是 `patches_enabled` 数组里的哈希（同一个公式）；帧数高于 120 时把 Knob Fix 的哈希加进去，否则移除。它的 description 同样不能随便改；v1.3.1 改过一次，旧文字放在 `$KnobDescOld`，安装和还原都会把旧描述算出的哈希从 `patches_enabled` 里删掉（以后再改描述，也要把旧文字加进去）。
- **Monitor Refresh Rate**：即 `spicetools.xml` 里 Sound Voltex 的 `graphics-force-refresh`，它强制游戏全屏模式（1080×1920）使用这个刷新率。所以只在显示器的 1080×1920（或 1920×1080）模式里有这个刷新率时才写，否则游戏建不起全屏、启动失败（用户反馈：VG27AQ1A 竖屏桌面 1440×2560@170Hz，按桌面分辨率判断后写了 170，游戏启动不了，改回 120 才能进；日志里游戏全屏切到 1080×1920@120）。竖屏时建议列表也改用 1080×1920 下的刷新率；原来的值在 1080×1920 下不可用时（比如旧版安装器写的 170）清空。写入条件：竖屏总是写（没有这项就插入）；横屏只在原来就设过时同步成新值。输入前列出游戏显示器支持的刷新率并建议从中选；填了不支持的数会提醒（横屏：不顺滑或撕裂；竖屏：垂直同步下 Live2D 速度会不对），玩家确认后才继续，`-Yes` 时只提醒。
- 改动的每个文件首次都备份为 `*.before-fps-unlock.bak`，保持原文件的 BOM。

参数：`-GameDir <路径>`、`-Fps <帧数>`、`-Yes`（不提问，没给 `-Fps` 时用默认值）、`-Restore`（还原，`restore.bat` 就是带这个参数运行）。

### 还原（restore.bat）

还原只用安装器第一次改文件时留下的 `*.before-fps-unlock.bak`，在版本检查之前执行，所以游戏更新、安装器不支持新版本时也能用。要确认（`-Yes` 跳过，取消时退出码 9，不改文件）。

- **补丁文件**（`patches\*.json`）：有备份、且当前文件还含 Frame Limiter / Knob Fix 项 → 用备份整份换回；当前文件已经不含（比如在 spice 里从补丁服务器更新过）→ 只删掉旧备份；含这两项但没有备份 → 提醒并保留文件，只撤销选择。
- **spice 补丁选择**：对上面涉及的每个补丁文件，把 Game FPS Target、Note FPS Target、Frame Limiter 的选择和 Knob Fix 的开关改回备份里的值（备份里没有就删掉）；`auto_apply` 里当前游戏那条，备份里没有就删掉。其余内容不动，所以安装后在 F4 里改的按键、别的补丁都保留。
- **Monitor Refresh Rate**：Sound Voltex 段里 `graphics-force-refresh` 这一行改回备份里的样子；备份里没有这一行（安装器插入的）就连同换行一起删掉。
- 处理完的备份删除，下次安装重新备份。

回归测试（模拟目录，2026101300 的 dll 和真实配置副本）：首次安装 300（三个已有哈希键的值被更新，没有新增键）；自定义 175 并重复运行（文件逐字节相同）；特征码 0 处 / 2 处（退出码 6，文件不变）；帧数 30（退出码 7，文件不变）；没有 log 和 spice 配置（提示手动选）；交互输入非法值后重新输入；空配置（补全 `auto_apply` 和三项选择）；竖屏写刷新率的替换 / 插入（只改这一行，BOM 和 CRLF 保留）。2026071400 的 dll 本机没有，这一版只改了配置写入部分，dll 定位逻辑和之前一样。

加入 Knob Fix 后再测（同样的模拟目录，补丁文件和 spice 配置用安装前的备份）：首次装 300（补丁文件里 Knob Fix 在 Frame Limiter 后面，偏移处正是 `F20F59CA`，`patches_enabled` 只多了它一个哈希）；重复运行逐字节相同；改 120 移除哈希、再改 300 加回；旧版安装器装过的目录直接升级；Knob 特征码 0 处 / 2 处（提醒并跳过，退出码 0，其余三项照常）；没有 spice 配置时手动提示多一行「再勾上 Knob Fix」；限帧器特征码 0 处仍是退出码 6、文件不变；填 60 不开 Knob Fix。只做了模拟目录测试，还没在游戏里实测。

还原的测试（同样的模拟目录）：装 300 后还原（补丁文件逐字节回到原样，spice 配置内容一致，不留备份）；再还原一次（提示没有需要还原的）；装完后改了别的选择和设置再还原（只撤销安装器的项，`auto_apply` 里安装器加的那条被删）；Monitor Refresh Rate 原来没有这行 / 原来是空值两种（都还原成逐字节相同）；装完后 dll 换了版本（安装退出码 2）照样能还原；回答 n 取消（退出码 9，文件不变）；补丁文件已被替换成原版（只删旧备份）；旧版安装器装过、新版再装、再还原（回到最初）。改动后安装的各项测试重跑一遍，结果不变。

竖屏判断的测试（本机桌面是横屏 2560×1600）：日志里没有模式记录（按桌面当横屏，不动 spicetools.xml）；上次启动 1080×1920@120（当竖屏，写入 Monitor Refresh Rate 300，还原后 spicetools.xml 逐字节回到原样）；上次启动 1080×1920@60（当横屏，不动 spicetools.xml）。没有在启动时才转屏的真实环境里测过。

## Live2D 动画速度

有反馈说解锁帧数后 Live2D 角色动画变快。查下来，**按推荐设置使用时不会变快**，没有做补丁。

Live2D（Cubism Framework，基于官方 sample 的 `LAppModel` / `LAppLive2DManager`，游戏自己包了一层 `CCubismModel`）每帧的 deltaTime 来源：

1. 主循环 `0x5a3000`（由 `0x3e687b` 调用）每帧读限帧器：`rate = target != 0 ? target : base`（`0x5a3581`–`0x5a359c`，乘 0.001 得 Hz）。
2. `0x5a3924`–`0x5a3938`：`dt = 1.0 / rate`，写入全局 double `0xbaf8e0`。同一个 `1/rate` 也在 `0x5a3604` 传给 afp-core 序号 15（2D 动画引擎）。
3. 随后遍历 Live2D 管理器里的所有模型，调用 `0x6c4450`（LAppModel::Update，`0x5a3983`，模型 +0x298 为暂停标志）。
4. `0x6c4450` 开头 `dt = (float)[0xbaf8e0]`，动作、表情、眨眼、呼吸（`sin(t·2π/周期)`）、物理（`0x6d5910`，标准 Cubism 物理，MaxDeltaTime 5.0）、视线跟随全部用这个 dt 累加时间，最后调用 `csmUpdateModel`（`0x7ae880`，唯一调用点 `0x6c4aaa`）。
5. `0xbaf8e0` 只有两处写入：上面的主循环，以及 `0x6c7bd7` 置 0。`0x6c4450` 只有主循环一个调用者，`CCubismModel`（`0x258d10` 创建）包的也是同一个 LAppModel，走同一条路径。游戏侧代码（`0x259xxx`、`0x61bxxx`）只调用开始动作、设参数这类接口，没有按帧推进动画。

所以 Live2D 的时间步长 = 1 / 限帧器速率，不是实际测出的帧间隔。限帧器有三条分支（`0x5a1974` 起），由 `AppMode` 决定：

| AppMode | base | target |
|---|---|---|
| `UFC` | 120000（补丁改这里） | 不开垂直同步时 = base；开垂直同步时 = 0 |
| `KFC` | 60000 | 同上 |
| 其它 | 60000 | 不设（0） |

是否开垂直同步看 `0x5a103f` / `0x5a10a4`：`D3DPRESENT_INTERVAL_ONE` 时 r15d=1，target 写 0（不软件限帧，靠垂直同步定帧率）；`INTERVAL_IMMEDIATE` 时 r15d=0x80000000，target=base。

结论：

- **横屏 / `INTERVAL_IMMEDIATE`**（日志里 `Using D3DPRESENT_INTERVAL_IMMEDIATE`）：帧率由限帧器决定，dt 正好等于帧间隔，Live2D 速度正常。2026101300 实机 300 FPS 就是这种情况。
- **竖屏 / 垂直同步**：帧率等于显示器刷新率 M，dt 仍是 1/N（N 为 Frame Limiter Target）。M = N 时正常；M > N 时 Live2D 快 M/N 倍，M < N 时变慢。比如 Monitor Refresh Rate 设了 180、Frame Limiter 还是默认 120，就会快 1.5 倍。按安装脚本提示把这几项设成同一个数就不会出现。
- `AppMode` 不是 `UFC` 时补丁不影响限帧器，dt 固定 1/60。

另有反馈说“机关枪”谱面没放完就碎屏。谱面事件 `LIVE2D_GRACE_GUN1/GUN2/FLY/FINAL`（`0x6f823` 等）只是把事件名映射到动作编号（表在 `0xbb2730` 起），在谱面时间点播放 `grace_sudden_game` 等模型的动作；碎屏发生在动作内部，动作按上面的 dt 推进。所以只有 Live2D 本身变快时碎屏才会提前，也就是垂直同步下 M > N 的情况，设置一致时不会出现。

对照：反馈里说的是 MixxioN [MXM 20]（BPM 275，模型 `grace_mixxion_game`）。B 站 2022-03-28 上传的未打补丁实机视频「[SDVX] MixxioN [MXM20] PUC」里，碎屏也是在谱面中途出现（CHAIN 约 1078，全曲 2:28，视频播到约 1:13），之后歌曲继续。这是这首歌本来的演出，不是解锁帧数导致的。

想做一个与设置无关的修正，只能把 `0x5a3924` 换成用 QPC 实测帧间隔（主循环在 `0xba3100` 已有 120 项 QPC 环形缓冲），这需要代码洞。目前设置一致时没有问题，不值得增加这个风险。

## 菜单旋钮（issue #1）

反馈（竖屏 1080×1920@480Hz，2026102700，FauceTwo+）：选曲界面旋钮转慢了没反应，键盘绑的旋钮也选不了歌；不用本工具、只把 `-graphics-force-refresh` 调到 120 以上也一样。以下地址是 2026101300。

选曲、选难度、排序、ExTrack 选关、刷卡注册（`CCardEntryRegistScene`）等界面都通过 `0x2642f0(旋钮, 档位)` 取「这一帧转了几格菜单」。数据来源：

1. `0x263b40` 返回一张静态表：2 个旋钮 × 4 档步长（1 / 85 / 128 / 170，一圈 1024 格），每项 0x88 字节，结果在 +0x80。
2. 主循环 `0x5a3000` 每帧调用 `0x266240`：对每项读 10 位旋钮值，交给滤波 `0x262d90` 得到本帧格数 n；n 为 0 的帧连续 120 帧（按帧数算）就清空累计；累计 ÷ 步长 = 菜单步数，余数留到下一帧。
3. 滤波 `0x262d90`（dt = 距上一帧的毫秒数 × 0.12，即以 1/120 秒为 1；d = 本帧旋钮变化，绝对值 ≥ 170 当 0）：
   - |d| ≤ 2（慢转）：`acc += 10·d·dt`；|acc| ≥ 30 定方向；|acc| ≥ 60.0 才出格：n = trunc((|acc| − 60) × 0.1)，acc −= 10n；acc 每帧向 0 回落 dt（每秒 120）。
   - |d| ≥ 3（快转）：n = d 直接放行，acc 清零。
   - 方向改变要持续 5（按 dt 算，约 42ms）才生效。

问题在慢转那一行乘了 dt：d 本来就是这一帧转过的量，再乘帧间隔，帧数为 N 时慢转只剩 120 帧时的 120/N，回落速度却按时间不变，所以慢转攒不起来。快转门槛是「一帧 ≥ 3 格」，480 帧时要转到 120 帧时的 4 倍快。按反汇编写的模拟（转速有波动）：慢转 0.2–0.5 圈/秒、步长 128 时，120 帧每圈 5–7 步，480 帧只有 1–2 步；去掉乘 dt 后 480 帧为 6–7 步。120 帧时 dt 本来约等于 1（毫秒取整，0.96 / 1.08 交替），去掉对 120 帧几乎没有影响。

**补丁 Knob Fix for High FPS**：把 `mulsd xmm1, xmm2`（`F2 0F 59 CA`，`0x262e7d`）换成 4 字节 NOP（`0F 1F 40 00`）。特征码从前面的 `lea eax, [r9+r9*4]` 起：

```
43 8D 04 89          lea      eax, [r9+r9*4]
03 C0                add      eax, eax
66 0F 6E C8          movd     xmm1, eax
F3 0F E6 C9          cvtdq2pd xmm1, xmm1
F2 0F 59 CA          mulsd    xmm1, xmm2      ← 改这里（特征码起点 +14）
F2 0F 58 4F 18       addsd    xmm1, [rdi+18h]
```

2026101300 里唯一命中。

另外两处没有改：

- 阈值 60.0 就是 `0x9844e8`，也就是 Game FPS Target 改的那个常量（全 dll 只有这一个 60.0，引用只有 `0x262d90` 和 `0x3e5850`）。Game FPS Target 设成 N 时阈值也变成 N，慢转要多攒才出第一格。模拟里修了 dt 之后这部分影响已经很小；要彻底分开得另找地方放一个 60.0，暂不做。
- 120 帧清空累计按帧数算（`0x2662ba` 的 `cmp dword [rdi], 78h`，单字节立即数最大 127），480 帧时是 0.25 秒没有输出才清空，模拟里不影响。

查过但不受影响的：`cPadTickVol`（`0x4ed330`，同样按帧判断）只有测试菜单 `NewIOGetTickCountTest` 用；刷卡界面 `CCardEntryScene` 用 `cPadVol`，增量来自 `0x61a8a0`：`(cur>>8) − (prev>>8)`，逐帧相加正好是总转量，和帧数无关。游戏内激光光标 `GameInputTumamiCursor` 用 `0x462570`，每帧变化不超过 96/65536（UFC）当 0，高帧数下可能也会吃掉慢速移动，还没有反馈，没有处理。

## 已知限制

- 代码里还有大量写死的 `1/120`（double / float 常量十余处）和 `120.0f`（27 处引用），这部分不随帧率变化。
- 竖屏 1080×1920 显示器上，游戏全屏会请求 120Hz + `D3DPRESENT_INTERVAL_ONE`，帧数被垂直同步锁住，需要 spice2x 的 `-graphics-force-refresh`（Monitor Refresh Rate）。平时横屏、启动时才转竖屏的，安装器要靠上次启动的日志才能认出来；还没这样启动过（或日志被删）时会按横屏处理，不写这一项。
- 横屏显示器上游戏退回 60Hz + `INTERVAL_IMMEDIATE`，只受内部限帧器控制。
- Game FPS Target 改的 60.0 同时是菜单旋钮滤波的阈值（见「菜单旋钮」），设得越高慢转越难出第一格。

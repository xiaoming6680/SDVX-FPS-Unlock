# 逆向记录

分析对象：`soundvoltex.dll`，版本 `KFC:J:G:A:2026101300`（PE TimeDateStamp `0x6ac4e43b`，入口 `0x7ad8d8`）。
以下地址均为 RVA，另注明的除外。工具：Python + capstone 线性反汇编、RIP 相对引用索引。

## 现象

- 游戏 Present 用的是 `D3DPRESENT_INTERVAL_IMMEDIATE`（不开垂直同步），在 300Hz 屏幕上帧数仍精确为 120.00。
- 已有的 Game FPS Target / Note FPS Target 补丁设成 300 后帧数不变，说明另有限帧逻辑。

## 已有的两个补丁做了什么

- `GetMainDisplayRefreshRate`（`0x3e5850`）：通过 NVAPI（`NvDisplayConfig`）读主显示器刷新率，返回 double（Hz）。
  读取失败时返回 `.rdata` 里的常量 60.0（`0x9844e8`），并打印 `(DUMMY)`。
- **Game FPS Target**：改的就是这个 60.0 回退值。
- **Note FPS Target**：把 `movd xmm6, eax; cvtdq2pd; mulsd [0.001]`（毫赫兹转赫兹）替换为 `mov eax, N; cvtsi2sd xmm6, eax`，
  即无论屏幕多少 Hz，都告诉游戏刷新率是 N。音符滚动速度按这个值计算。

## 内部限帧器

一个全局对象，位于 `0x12d4780`（由函数局部 static 守卫 `0x12d4778` 初始化）：

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0 | int32 | 基础帧率，毫赫兹，初始 60000 |
| +4 | int32 | 目标帧率，毫赫兹，0 表示不限帧 |
| +8 | int64 | 下一帧截止时间，纳秒 |

相关函数：

| RVA | 作用 |
|---|---|
| `0x6119b0` | 取对象指针（17 处调用） |
| `0x6119f0` | `set(rate)`：写 +0，清 +4，重置截止时间 |
| `0x611a40` | 重置截止时间为当前时间 |
| `0x611a90` | 等待：+4 非 0 时，截止时间 += 1e12 / rate，然后 `SwitchToThread` 自旋到截止时间 |

设置点在 `0x5a1979` 附近（显示初始化流程）：

```
edi = 60000
if (check_0x1d5c90()) {             // 当前环境走这一支
    lim->set(120000)                // 0x5a1987: mov ebx, 0x1d4c0
    lim->target = has_cfg ? cfg : 120000
    lim->reset()
} else if (check_0x1268d0()) {
    lim->set(60000); lim->target = has_cfg ? cfg : 60000; ...
} else {
    lim->set(60000)
}
```

`0x5a1a20` 起的函数会把「有效帧率」（target 非 0 取 target，否则取 base）返回给游戏其他部分，所以一部分逻辑会随之缩放。

## 补丁

把 `0x5a1987` 的 `mov ebx, 120000`（`BB C0D40100`，文件偏移 `0x5a0f87`）改成 `mov ebx, N*1000`。
三项补丁需取同一个 N：限帧器决定实际帧数，Game/Note FPS Target 让游戏按同一速率计算。

安装脚本用特征码定位，不写死偏移：

```
BB C0 D4 01 00   mov ebx, 120000
8B D3            mov edx, ebx
48 8B C8         mov rcx, rax
E8               call set
```

要求在整个 dll 里**正好命中一处**。2026101300 与 2026071400 两个版本均唯一命中。

## 补丁文件

spice2x 按 `patches/KFC-<TimeDateStamp:08x>_<AddressOfEntryPoint:x>.json` 加载补丁。脚本：

1. 读 dll 的 PE 头得到文件名。
2. Game FPS Target：校验 dll 中 60.0 的 8 字节（`0000000000004E40`），改为写 double 的高 2 字节，使所有档位覆盖同一范围（原补丁只写 1 字节，180 / 185 等需要 2 字节）。
3. Note FPS Target：校验 60 档原始字节，按 120 档的指令格式生成其他档位。
4. 插入 Frame Limiter Target 联合补丁，重复运行结果相同；首次运行备份原文件。

档位 = 预设（60 / 120 / 144 / 165 / 180 / 185 / 240 / 300）加上玩家输入的数（60–1000）。Game FPS Target 只写 double 的第 5、6 字节，最高字节固定 `0x40`，2–8191 的整数都能精确表示。

### 安装器自动完成的设置

- **显示器**：`EnumDisplayDevices` / `EnumDisplaySettings` 列出每个显示器当前分辨率下支持的刷新率。游戏显示器取 `spicetools.xml` 里 Sound Voltex 的 `mainmonitor`，没设就取主显示器；高大于宽视为竖屏。默认目标帧数 = 游戏显示器最高刷新率。
- **配置文件位置**：从 `contents\log.txt` 开头记录的上次启动参数读 `-cfgpath`（`spicetools.xml`）和 `-patchcfgpath`（补丁选择），相对路径相对 `contents`。读不到时依次找 `contents\`、`%APPDATA%\spice2x\`、`%APPDATA%\`。都没有就提示玩家在 F4 里手动选。
- **补丁选择**：spice2x 把联合补丁的选择存在 `union_patches_enabled`，键为 `sha256(补丁的 gameCode + 补丁文件名（不含 .json） + 补丁名 + description)` 的小写十六进制，值为选中的档位名。本机配置里 8 个补丁的哈希全部按这个公式复现。安装器写入三项的档位名，并把 `prop\ea3-ident.xml` 的 `model:dest:spec:rev:ext` 加进 `auto_apply`（spice 启动时按它自动套用已保存的选择）。所以 Frame Limiter 的 description 不能随便改，改了哈希就变，旧的选择会失效。
- **Monitor Refresh Rate**：即 `spicetools.xml` 里 Sound Voltex 的 `graphics-force-refresh`。目标帧数是游戏显示器支持的刷新率时才写：竖屏总是写（没有这项就插入）；横屏只在原来就设过时同步成新值。竖屏且显示器不支持时会提醒（垂直同步下 Live2D 速度会不对），玩家确认后才继续。
- 改动的每个文件首次都备份为 `*.before-fps-unlock.bak`，保持原文件的 BOM。

参数：`-GameDir <路径>`、`-Fps <帧数>`、`-Yes`（不提问，没给 `-Fps` 时用默认值）。

回归测试（模拟目录，2026101300 的 dll 和真实配置副本）：首次安装 300（三个已有哈希键的值被更新，没有新增键）；自定义 175 并重复运行（文件逐字节相同）；特征码 0 处 / 2 处（退出码 6，文件不变）；帧数 30（退出码 7，文件不变）；没有 log 和 spice 配置（提示手动选）；交互输入非法值后重新输入；空配置（补全 `auto_apply` 和三项选择）；竖屏写刷新率的替换 / 插入（只改这一行，BOM 和 CRLF 保留）。2026071400 的 dll 本机没有，这一版只改了配置写入部分，dll 定位逻辑和之前一样。

## Live2D 动画速度

有反馈说解锁帧数后 Live2D 角色动画变快。查下来，**按推荐设置使用时不会变快**，没有做补丁。

Live2D（Cubism Framework，基于官方 sample 的 `LAppModel` / `LAppLive2DManager`，游戏自己包了一层 `CCubismModel`）每帧的 deltaTime 来源：

1. 主循环 `0x5a3000`（由 `0x3e687b` 调用）每帧读限帧器：`rate = target != 0 ? target : base`（`0x5a3581`–`0x5a359c`，乘 0.001 得 Hz）。
2. `0x5a3924`–`0x5a3938`：`dt = 1.0 / rate`，写入全局 double `0xbaf8e0`。同一个 `1/rate` 也在 `0x5a3604` 传给 afp-core 序号 15（2D 动画引擎）。
3. 随后遍历 Live2D 管理器里的所有模型，调用 `0x6c4450`（LAppModel::Update，`0x5a3983`，模型 +0x298 为暂停标志）。
4. `0x6c4450` 开头 `dt = (float)[0xbaf8e0]`，动作、表情、眨眼、呼吸（`sin(t·2π/周期)`）、物理（`0x6d5910`，标准 Cubism 物理，MaxDeltaTime 5.0）、视线跟随全部用这个 dt 累加时间，最后调用 `csmUpdateModel`（`0x7ae880`，唯一调用点 `0x6c4aaa`）。
5. `0xbaf8e0` 只有两处写入：上面的主循环，以及 `0x6c7bd7` 置 0。`0x6c4450` 只有主循环一个调用者，`CCubismModel`（`0x258d10` 创建）包的也是同一个 LAppModel，走同一条路径。游戏侧代码（`0x259xxx`、`0x61bxxx`）只调用开始动作、设参数这类接口，没有按帧推进动画。

所以 Live2D 的时间步长 = 1 / 限帧器速率，不是实际测出的帧间隔。限帧器有三条分支（`0x5a1974` 起），由 `AppMode` 决定：

| AppMode | base | target |
|---|---|---|
| `UFC` | 120000（补丁改这里） | 不开垂直同步时 = base；开垂直同步时 = 0 |
| `KFC` | 60000 | 同上 |
| 其它 | 60000 | 不设（0） |

是否开垂直同步看 `0x5a103f` / `0x5a10a4`：`D3DPRESENT_INTERVAL_ONE` 时 r15d=1，target 写 0（不软件限帧，靠垂直同步定帧率）；`INTERVAL_IMMEDIATE` 时 r15d=0x80000000，target=base。

结论：

- **横屏 / `INTERVAL_IMMEDIATE`**（日志里 `Using D3DPRESENT_INTERVAL_IMMEDIATE`）：帧率由限帧器决定，dt 正好等于帧间隔，Live2D 速度正常。2026101300 实机 300 FPS 就是这种情况。
- **竖屏 / 垂直同步**：帧率等于显示器刷新率 M，dt 仍是 1/N（N 为 Frame Limiter Target）。M = N 时正常；M > N 时 Live2D 快 M/N 倍，M < N 时变慢。比如 Monitor Refresh Rate 设了 180、Frame Limiter 还是默认 120，就会快 1.5 倍。按安装脚本提示把这几项设成同一个数就不会出现。
- `AppMode` 不是 `UFC` 时补丁不影响限帧器，dt 固定 1/60。

另有反馈说“机关枪”谱面没放完就碎屏。谱面事件 `LIVE2D_GRACE_GUN1/GUN2/FLY/FINAL`（`0x6f823` 等）只是把事件名映射到动作编号（表在 `0xbb2730` 起），在谱面时间点播放 `grace_sudden_game` 等模型的动作；碎屏发生在动作内部，动作按上面的 dt 推进。所以只有 Live2D 本身变快时碎屏才会提前，也就是垂直同步下 M > N 的情况，设置一致时不会出现。

对照：反馈里说的是 MixxioN [MXM 20]（BPM 275，模型 `grace_mixxion_game`）。B 站 2022-03-28 上传的未打补丁实机视频「[SDVX] MixxioN [MXM20] PUC」里，碎屏也是在谱面中途出现（CHAIN 约 1078，全曲 2:28，视频播到约 1:13），之后歌曲继续。这是这首歌本来的演出，不是解锁帧数导致的。

想做一个与设置无关的修正，只能把 `0x5a3924` 换成用 QPC 实测帧间隔（主循环在 `0xba3100` 已有 120 项 QPC 环形缓冲），这需要代码洞。目前设置一致时没有问题，不值得增加这个风险。

## 已知限制

- 代码里还有大量写死的 `1/120`（double / float 常量十余处）和 `120.0f`（27 处引用），这部分不随帧率变化。
- 竖屏 1080×1920 显示器上，游戏全屏会请求 120Hz + `D3DPRESENT_INTERVAL_ONE`，帧数被垂直同步锁住，需要 spice2x 的 `-graphics-force-refresh`（Monitor Refresh Rate）。
- 横屏显示器上游戏退回 60Hz + `INTERVAL_IMMEDIATE`，只受内部限帧器控制。
